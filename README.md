# WARPOINT на Next.js

Порядок дальнейшей работы, расположение компонентов и список незавершённых интеграций: [WORKFLOW.md](WORKFLOW.md).

Самостоятельное Next.js-приложение WARPOINT. Доступны главная, каталог игр, тарифы, статьи, политика конфиденциальности, локации и три страницы мероприятий. Каждая страница отдаётся сервером для города, выбранного по `Host`, и содержит готовые HTML, title, description и canonical. Старые адреса `main.html`, `event_dr.html`, `event_corp.html`, `event_graduation.html` перенаправляются на новые маршруты.

## Запуск

```powershell
cd D:\projects\warpoint-next
npm install
npm run dev
```

Откройте `http://localhost:3002/`. На `/` временно расположен список страниц; основная страница находится на `/indexpage/`. Для локального просмотра конкретного города задайте `PREVIEW_SITE_HOST` равным хосту из ERP. На адресах `*.vercel.app` эта же переменная выбирает город для предпросмотра; на рабочих доменах используется хост запроса. Нужен сетевой доступ к `https://gserver.warpoint.ru/api/site/v2/countries`; его можно переопределить через `ERP_COUNTRIES_URL`.

```powershell
$env:PREVIEW_SITE_HOST = 'kursk.warpoint.ru'
npm run dev
```

Для проверки продакшен-сборки:

```powershell
npm run build
npm run start
```

Страницы состоят из JSX-компонентов в `components/site`; их порядок задают `HomeSections`, `BirthdaySections`, `CorporateSections` и `GraduationSections`. SSR подставляет данные города и арены через `siteFields`. Разметка не читается из HTML-файлов классического проекта `D:\projects\warpoint\src` и не вставляется через `dangerouslySetInnerHTML`.

Весь код и все медиафайлы находятся в этом проекте: JSX в `components`, SCSS в `styles`, изображения, шрифты, видео и SVG-спрайт в `public`. Next.js собирает SCSS напрямую. Классический проект на Vite не нужен для запуска или сборки приложения. Новые изображения и видео добавляйте в `public`.

Маршруты: `/` (временный список), `/indexpage`, `/games`, `/tariffs`, `/promotions`, `/articles`, `/articles/birthday-ekaterinburg`, `/faq`, `/events`, `/events/birthday`, `/events/corporate`, `/events/graduation`, `/locations`, `/legal/privacy`, `/sitemap.xml`, `/robots.txt`.

## Развёртывание на Vercel

1. Отправьте изменения в отдельный GitHub-репозиторий `Soveliy/warpoint-next`.
2. В Vercel выберите **Add New → Project**, импортируйте `Soveliy/warpoint-next`. Корневая папка проекта — `./`, Framework Preset — **Next.js**. Команды сборки и папку результата оставьте определёнными автоматически.
3. В **Settings → Environment Variables** добавьте `PREVIEW_SITE_HOST=warpoint.ru` для Preview и Production, чтобы адреса `*.vercel.app` открывали Екатеринбург. Для предпросмотра другого города укажите точный хост из поля `links.site_url` в ERP. `ERP_COUNTRIES_URL` и `ERP_REVALIDATE_SECONDS` необязательны: по умолчанию используются публичный API и 300 секунд.
4. Запустите Deploy и проверьте `/`, `/indexpage/`, `/events/birthday/`, `/robots.txt` на выданном адресе `.vercel.app`. Такие адреса закрыты от индексации; canonical указывает на выбранный рабочий домен.
5. Рабочие домены добавьте через **Project Settings → Domains** после проверки предпросмотра. Внесите `warpoint.ru` и нужные поддомены, которые указаны в ERP. Для wildcard-домена (`*.warpoint.ru` или другого) Vercel требует перенос DNS на его nameservers. До переключения рабочего домена убедитесь, что запись ERP и SSL готовы.

Поддомены с неизвестным для ERP хостом получают 404. Настройка доменов и DNS выполняется отдельно от первого деплоя на `.vercel.app`.

## Переключение шрифта заголовков

Вместо Roboto Flex сейчас используется Oceanic Grotesk Condensed ExtraBold. Основной текст и интерфейс остаются на Inter Tight. Общий переключатель — `secondaryFont` в `lib/typography.js`: значение `'oceanic'` включает новый вариант, `'roboto-flex'` возвращает прежние заголовки. После изменения пересоберите и задеплойте сайт; локально достаточно обновить страницу. Исходный Roboto Flex и его настройки сохранены, но при выборе Oceanic этот шрифт не предзагружается.

## Данные и ограничения

Онлайн-бронирование открывается из «Забронировать → Забронировать онлайн» на главной странице. Основной сайт подключает отдельное приложение через iframe в `components/site/BookingFrame.jsx`, стили оболочки находятся в `styles/components/_booking-frame.scss`. Семь шагов, авторизация, демонстрационные тарифы и расписание находятся в проекте `D:\projects\warpoint-booking`. Запуск и встраивание описаны в [README приложения бронирования](D:/projects/warpoint-booking/README.md).

Для production задайте `NEXT_PUBLIC_BOOKING_WIDGET_URL` равным HTTPS-адресу опубликованного приложения бронирования. Пример переменной находится в `.env.example`. Значение встраивается при `next build`, поэтому после изменения нужен повторный деплой основного сайта. В development автоматически используется `http://localhost:3004/`. При пустом URL в production диалог предлагает вернуться к заявке.

Финальное действие формы создаёт предварительный расчёт и событие `warpoint:booking-request` с `preview: true`. Для проверки промокодов, сертификатов и бонусов, создания брони, SMS и оплаты потребуется согласованный API.

ERP определяет город, адреса, режим работы, координаты и ссылки бронирования. Эти данные подставляются в шапку, список адресов и формы выбора локации. Выбор другого города ведёт на хост, указанный в `links.site_url`; город не меняется только в браузерном хранилище. Цена из статической вёрстки отображается лишь для Екатеринбурга: API `countries` не содержит тарифов для остальных городов. Для иных городов показана цена по запросу.

Блок контактов реализован в JSX; переключение арены обновляет адрес, карту, маршрут и ссылку бронирования. ERP пока возвращает пустые координаты для трёх клубов Екатеринбурга, поэтому для них сохранены ранее заданные координаты. Если у другой арены координат нет, вместо неверной точки на карте показывается адрес.

В текущем ответе ERP хост `warpoint.ru` указан для Екатеринбурга и Минска. Пока нет однозначного адреса в ERP, на этом хосте выбран Екатеринбург, а конфликтующая ссылка Минска скрыта из списка городов. Если хост в API не найден, страница возвращает 404. Ответ ERP кешируется на 300 секунд; период можно изменить через `ERP_REVALIDATE_SECONDS`. Перед продуктивным запуском следует согласовать резервное поведение при недоступности ERP.

Разметка страниц перенесена в React-компоненты с серверным HTML. Шапка, выбор города и арены, контакты, FAQ, анкета праздника, модальные окна, анонс, видео и уведомление о cookie управляются состоянием React. GSAP-анимации, Swiper, Fancybox, Яндекс Карты и маска телефона запускаются в клиентском эффекте из локальной папки `interactions`; они остаются интеграциями внутри Next.js. Формы событий создают событие `warpoint:event-quiz-complete`; эндпоинт отправки заявок в ERP не был предоставлен. Формы каталога и тарифов открывают подготовленное письмо пользователю. Для прямого приёма заявок потребуется согласованный API.

Каталог показывает семь подтверждённых игр из локальных данных; счётчик и фильтры отражают реальное количество. Тарифы арены, ВР-станции и зоны экстрим взяты из предоставленных макетов. Вкладки симуляторов и комбо остаются без цен до получения подтверждённых данных. На странице статей пока доступны только четыре анонса из макета: полные тексты не предоставлены, поэтому ссылки чтения не показываются. Политика конфиденциальности перенесена с действующей страницы WARPOINT; остальные юридические тексты ожидаются.

## API сайтов

Локальная интеграция нового GET /api/wp_site/public/sites/ включается серверной переменной ERP_SITE_TOKEN. Адрес задаётся в ERP_SITES_URL. Токен хранится в игнорируемом .env.local, обращение к ERP выполняет сервер. Без токена используется прежний справочник стран.

Контент, тарифы, доступность игр и зон привязаны к UUID выбранного парка. Суммы тарифов приходят в копейках. Даты анонсов отображаются в IANA-часовом поясе города, при его отсутствии используется UTC. Пустой список в API означает отсутствие опубликованных данных. Адреса и контакты дополняются из прежнего ERP, когда парк найден по UUID или названию в том же городе.

Данные dserver пока проверяются локально. Создание брони, расписание, авторизация клиента и оплата требуют отдельных контрактов API.
